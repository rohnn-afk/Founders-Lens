# Render Free staging

Deploy only synthetic data and the authenticated read surface. [render.yaml](render.yaml) declares Free Next.js and Express web services and one Free Render PostgreSQL primary, all in Oregon. The API also requires a separately provisioned PostgreSQL privacy authority. Render allows only one Free PostgreSQL instance per workspace, so a single Free Blueprint cannot provision both independent clusters. A second database or schema on the primary cluster does not satisfy the authority check. Leave Redis, dispatcher, worker, provider keys and hosted writes disabled. [Render Free limits](https://render.com/docs/free)

## Configure and bootstrap

1. Review the Blueprint in a workspace with a Free Postgres slot. Verify that all three declared resources are Free before approving creation. Connect both web services to the reviewed GitHub repository's `staging` branch. Both builds run from the repository root. The Blueprint runs `npm ci --include=dev`, then either `node scripts/next.mjs build --webpack` or `npm run db:generate && npm run build --workspace=@founders-lens/api`. Web starts with `node scripts/next.mjs start --hostname 0.0.0.0 --port "$PORT"`. API starts with `node apps/api/dist/main.js` and uses Render's `PORT`. Initial Blueprint approval can trigger builds, so approve the first sync only after the selected commit passes CI. Until the operator supplies valid clearance, the API will refuse startup.
2. Record the two assigned `https://…onrender.com` origins (no trailing slash). Configure a dedicated staging Clerk instance with the exact web origin and an audience claim matching the API. Set web's `NEXT_PUBLIC_FL_WEB_ORIGIN`, `NEXT_PUBLIC_FL_API_ORIGIN`, and `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` before building. Set `CLERK_SECRET_KEY` and `CLERK_AUTHORIZED_PARTIES` (JSON array containing the web origin) in both services. On API, set `FL_WEB_ORIGIN`, `CLERK_INSTANCE_ID`, `CLERK_ISSUER`, `CLERK_PUBLISHABLE_KEY`, and `CLERK_AUDIENCE` (nonempty JSON array). Web readiness checks the API through its configured public HTTPS origin. [Render environment configuration](https://render.com/docs/configure-environment-variables)
3. Verify the identity of the fresh `founders_lens_staging` primary. Use a dedicated migrator connection from an approved operator address and set `MIGRATION_DATABASE_URL` only for `node node_modules/prisma/build/index.js migrate deploy --config prisma.config.ts`. Create separate restricted logins `fl_p6_workspace` and `fl_p8_conversations` and apply `psql -v ON_ERROR_STOP=1 -f scripts/staging-read-grants.sql` against that primary with an authorized database and schema operator connection. Where external operator access is needed, allowlist only the operator address for that window and restore the Blueprint's closed external allowlist afterward. Set `FL_WORKSPACE_DATABASE_URL` and `FL_CONVERSATIONS_DATABASE_URL` on API using Render's **internal** primary hostname with those restricted credentials. Use the `postgresql://` scheme and percent-encode credentials. Never use the Blueprint database owner's connection string as either runtime URL. [Render PostgreSQL connections](https://render.com/docs/postgresql-creating-connecting)
4. Use the approved independent Neon staging database `neondb` (verified system identifier `7711490023970028889`). The existing `ledger_reader` passes the identity query over verified TLS. First verify the Render primary's system identifier and confirm it differs. Then obtain approval for a reviewed Neon bootstrap that targets `neondb` and reuses the existing reader. The [authority fixture](tests/fixtures/suppression-ledger-bootstrap.sql) targets `suppression_proof`, creates the reader, and changes PUBLIC privileges, so do not run it directly. After the approved bootstrap, verify empty intent history and seal coverage for retained version `[1]`. Configure API's `FL_AUTHORITY_DATABASE_URL` with the restricted reader and exactly `?sslmode=verify-full`. Keep authority writer credentials and the challenge derivation key on the operator side.
5. Bind one approved Clerk test user on the new primary through the operator workflow and prepare an owned synthetic idea or saved conversation. Configure the API with separate 64-hex-character keys for `FL_SUBJECT_KEY_V1`, `FL_CURSOR_KEY`, and `FL_AUTHORITY_INTEGRITY_KEY`. Set `FL_AUTHORITY_EPOCH`, `FL_AUTHORITY_NAMESPACE`, and `FL_OPERATOR_PUBLIC_KEY` (base64 Ed25519 SPKI DER). Keep the private signing key on the operator workstation.

## Smoke window

For a Neon application primary, use the [Neon staging initialization procedure](apps/api/STAGING-NEON.md) in place of the Render primary setup. Keep the existing authority project and reader. Set `FL_STAGING_PRIMARY_PROVIDER=neon` in the API service when saving the two verified Neon runtime URLs. The Blueprint retains the Render primary configuration for rollback.

1. Run the gated GitHub workflow only when a release can complete inside the five-minute decision window. Run `node scripts/staging-sign-read.mjs` on the operator workstation with the signer settings below. Install the resulting `FL_STAGING_IDEAS_DECISION` and `FL_STAGING_TRANSCRIPT_DECISION` on the API using Render's save-only option. With an independent reviewer, do this after CI passes and immediately before deployment approval. On the solo-maintainer path, the manual dispatch is the release authorization and starts CI before deployment. If CI and rollout cannot reliably fit into the remaining window, keep deployment credentials unset until a separately approved release procedure can supply fresh decisions at rollout. If evidence expires, let readiness fail.
2. Open the API's `/health/live` first to wake it, then check `/health/ready` on API and web. Both readiness endpoints must return `200` before testing. Render monitors `/health/live` so expiry is a readiness failure without repeatedly restarting a running service. A cold API startup still requires fresh decisions.
3. Sign in through web and open the owned workspace. Confirm an unauthenticated ideas request returns `401`, a foreign origin fails CORS, and a workspace POST returns `404`. After clearance expiry, readiness must return `503` and private reads must fail closed. [Render health checks](https://render.com/docs/health-checks)

Free web services sleep after 15 idle minutes and typically take about a minute to wake. Free instance hours are shared. Free Postgres expires after 30 days and has no managed backups. Treat the database as disposable and check workspace usage and billing before deployment. A replacement primary needs a new identity and new signed decisions. [Render Free limits](https://render.com/docs/free)

On the operator workstation, build the API before running the signer. Set `FL_CONFIRM_STAGING_READ=approve-staging-read-only`, the verified `FL_EXPECTED_PRIMARY_IDENTITY` and `FL_EXPECTED_AUTHORITY_IDENTITY`, `FL_OPERATOR_PRIMARY_READ_URL`, `FL_OPERATOR_AUTHORITY_READ_URL`, and the authority epoch, namespace, and integrity key. Set `FL_OPERATOR_PRIVATE_KEY_FILE` to the private signing key and `FL_STAGING_DECISION_OUTPUT` to a new private file outside the checkout.

## GitHub release gate and rollback

1. Protect `staging` with required GitHub Actions checks **Build and test** and **Secret and dependency checks**. Restrict the GitHub Actions environment named `staging` to the exact branch. Use an independent reviewer when one is available. For a solo-maintained repository, keep the environment branch-restricted and use explicit owner dispatch after the deployment gates are satisfied. The initial CI-only run needs no deploy credentials.
2. In that environment only, set the secret `RENDER_API_KEY` and variables `RENDER_STAGING_WEB_SERVICE_ID` and `RENDER_STAGING_API_SERVICE_ID`. Keep automatic deploys off on both Render services, and disable any competing deploy hooks or Blueprint auto-sync that would deploy code independently. Enable the GitHub repository connection for the intended Render workspace.
3. Dispatch **CI** on branch `staging` with **deploy_staging** selected. Both CI jobs must pass in that run. The deployment job verifies the two named Free staging services against the repository and branch before requesting the exact tested commit from Render. An accepted request means Render queued it. Verify both revisions and the smoke endpoints before declaring a deployment live. Production has no deployment job in this workflow.
4. Record the last known-good deploy IDs for both services. On a partial or uncertain rollout, inspect Render deploy history before dispatching again. Roll back the affected services to the matching known-good deploys. Confirm the same database targets, fresh signed clearance, and readiness. Application rollback does not roll back schema, database data, or authority history. A first deploy has no prior version to restore.

The API retains its existing sanitized startup, shutdown and request events, graceful connection draining, and exact-origin CORS. CI exercises PostgreSQL, independent authority, Redis and the BullMQ pipeline with disposable loopback fixtures and deterministic generation. Hosted workers, Redis, Groq, and database migrations stay outside the staging deploy workflow.

## Public portfolio demo

The public demo is a separate build mode of `founders-lens-staging-web`. It serves the landing page and an illustrative conversation without Clerk, the API, PostgreSQL, Redis, or AI providers. Workspace, sign-in, and Clerk proxy requests return 404. Demo readiness checks only the web process.

After publication approval and successful CI for the exact `staging` SHA, open **founders-lens-staging-web** in Render. Verify **Free**, branch **staging**, and **Auto-Deploy Off**. In **Environment**, add `FL_PUBLIC_DEMO=true`, keep `NODE_VERSION=24.22.3` and `SKIP_INSTALL_DEPS=true`, and save without deploying. Clerk keys, `CLERK_AUTHORIZED_PARTIES`, `NEXT_PUBLIC_FL_WEB_ORIGIN`, and `NEXT_PUBLIC_FL_API_ORIGIN` are unnecessary in this mode. Remove any such variables from this web service for the demo. Render supplies `PORT` and the actual HTTPS origin in `RENDER_EXTERNAL_URL`, which sets the page's canonical and social URLs.

| Setting | Value |
| --- | --- |
| Build command | `npm ci --include=dev && node scripts/next.mjs build --webpack` |
| Start command | `node scripts/next.mjs start --hostname 0.0.0.0 --port "$PORT"` |
| Health check | `/health/live` |

Select **Manual Deploy → Deploy a specific commit** on the web service and enter the CI-verified SHA. The shared staging workflow deploys the API too, so use the web service dashboard for the demo. Verify the deployed SHA and visit the HTTPS URL displayed on that service. Check the preview anchor, GitHub link, stylesheet, and mobile layout. Confirm 200 on `/health/live` and `/health/ready`, and 404 on `/app`, `/sign-in`, and `/__clerk`.

For rollback, roll back only the web service to its previous deploy in Render. Returning to hosted workspace mode requires a new build with `FL_PUBLIC_DEMO` removed and the authenticated workspace settings above restored.
