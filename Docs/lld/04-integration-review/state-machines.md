# Canonical state machines and authorities

**Status:** Approved Phase 2D documentation — A07, FL-P2D-1.0-approved. Runtime acceptance remains unexecuted; identified deployment/ancillary proposals remain tracked.

Status: proposed engineering reconciliation, except explicit disconnect/no-replay decision accepted. CAS [compare-and-swap: atomic update matching expected persisted state] and fencing [a monotonically increasing lease number rejecting stale workers] are mandatory persistence design obligations, not executed constraints.

## Generation

| From | To | Authority and guard |
|---|---|---|
| absent | PENDING | API acceptance transaction: owner active, quota reserved, message/attempt/outbox/ledger committed |
| PENDING | RUNNING | Worker claim: active owner/idea, unexpired deadline; increment leaseEpoch atomically |
| PENDING, RUNNING | CANCEL_REQUESTED | Owner API transaction; match current state; never overwrite terminal |
| RUNNING | COMPLETED | Epoch owner only: valid lease/deadline, active account/idea, validated output; insert response, settle usage and replace selection atomically |
| PENDING, RUNNING | FAILED | Worker or reconciler: bounded retry/deadline exhausted; valid epoch for running; settle reservation |
| CANCEL_REQUESTED | CANCELLED | Worker checkpoint or reconciler fences expired lease; discard output and settle usage |
| CANCEL_REQUESTED | FAILED | Reconciler only for unrecoverable reconciliation failure; sanitized reason, never select output |

COMPLETED/FAILED/CANCELLED immutable; no transitions out. Provider abort is best effort. Cancellation CAS first forbids completion and ordinary provider-failure writes (which require RUNNING); worker observes cancel then settles CANCELLED. Completion or failure CAS first returns that terminal state to cancellation. Cancellation accepted does not guarantee zero provider billing. No CANCEL_REQUESTED to COMPLETED. Retry before invocation reclaims PENDING with new epoch; RUNNING lease loss after ambiguous invocation fails safely instead of silently making another paid call. Regeneration creates a new attempt, never reopens a terminal one.

SRS §8.1 mapping: SUBMITTED/VALIDATED/REJECTED are admission processing, USER_MESSAGE_SAVED maps to committed PENDING, GENERATING to RUNNING; UI interruption does not mutate generation. CANCEL_REQUESTED is the durable stop request. This is a proposed clarification, not a silent SRS rewrite.

## Memory

PROPOSED -> ACCEPTED / EDITED_AND_ACCEPTED / DISMISSED / INVALIDATED. Only authenticated owner can accept/edit/dismiss; system may invalidate stale/ineligible proposals, never approve. API transaction checks proposal version and PROPOSED plus target memory expected version, writes confirmed current content/version and immutable MemoryRevision, records actor and proposal terminal result. Any failure rolls back all writes. Terminal review states never reopen; rejected/dismissed proposal cannot later be accepted. Editing pending text increments proposal version but leaves PROPOSED. Direct confirmed-memory corrections require owner and version, append revision and increment version atomically. Assumption statement lives in Assumption; revisions may quote historical text. Lifecycle purge is the explicit exception to history immutability.

## Research

NOT_NEEDED and LIMIT_REACHED are admission decisions; no external call. Persist accepted job as QUEUED -> RUNNING -> SUCCEEDED / INSUFFICIENT_EVIDENCE / FAILED. Worker/reconciler owns transitions under epoch, lease, account/idea guards; terminal immutable. Retry before unsafe invocation keeps job identity and increments delivery count; explicit new research request creates new job. SUCCEEDED requires at least one validated evidence record committed in the same final transaction. Empty retrieval yields INSUFFICIENT_EVIDENCE. Candidate evidence retains locator, publisher/title where available, retrievedAt, publication/observation time or explicit unknown, geography, applicable period, verification status and methodology/caveats. SOURCE_CHECKED is source verification, never automatic confirmation of a business claim. Each claim/source association must preserve provenance; detailed DTO remains D14. User observation and Learning interpretation remain distinguishable.

## Snapshots and exports

DocumentSnapshot: DRAFT -> REVIEWING -> APPROVED, owner only. Draft/reviewing edits use draftRevision and return to DRAFT; approve atomically checks version, persists approved actor/time and SHA-256 over versioned canonical UTF-8 content. APPROVED terminal/immutable; changes fork a new draft with new document version. draftRevision is distinct from immutable document version. Content schema/canonical serialization are specified in API §14; immutable-version policy A06 is approved; runtime parity proof remains a release gate.

ExportJob: QUEUED -> RUNNING -> COMPLETED / FAILED; worker/reconciler only, fenced as above. Retries within a bounded execution budget retain job identity; explicit retry after terminal failure creates new job referencing same approved snapshot/hash. SRS §8.6 EXPORT_REQUESTED/EXPORTED/EXPORT_FAILED are UI projections from jobs, not mutations of approved content. Render outside transaction with no substantive model regeneration. Upload private artifact under attempt-specific key, compute artifact checksum (distinct from content hash), then guarded completion stores key, checksum and snapshot hash. Failed finalization schedules orphan cleanup. Download checks owner, active lifecycle, completed job and snapshot integrity before grant. Engineering grant TTL default: five minutes under the approved bounded PDF-export decision; URLs never persisted in logs or replay ledger.

## Account and idea deletion lifecycle

Authoritative lifecycle: ACTIVE -> DELETION_REQUESTED -> PURGING -> DELETED. DISABLED accounts and ARCHIVED ideas may also enter DELETION_REQUESTED; neither can be reactivated by a webhook. Root status mirrors DataOperation.deletionState while the root exists; after hard removal, the retained minimal DataOperation is the authority. Its general execution status is separate: REQUESTED -> RUNNING -> WAITING_RETRY -> RUNNING, or REQUIRES_ATTENTION after exhausted automatic recovery, finally COMPLETED. A retry never sets the root ACTIVE. FAILED remains a terminal export-workflow outcome, not a completed deletion.

| Transition / authority | Atomic guard and effects | Recovery |
|---|---|---|
| ACTIVE/ARCHIVED/DISABLED -> DELETION_REQUESTED / owner API or verified user.deleted handler | Lock account then idea (if scoped); authorize owner; fresh-auth requirement below; create one scoped DataOperation, tombstone for account, ledger replay reference and outbox; increment lifecycle/version and context epoch | Commit before 202/204. Redis is not required for lifecycle gating; uncertain commit retries same intent |
| DELETION_REQUESTED -> PURGING / privacy worker or DB-polling reconciler | Claim operation epoch/lease, recheck scope/lifecycle; root and operation advance together; invalidate all older sensitive job leases | Expired claim reclaimed with higher epoch; no new founder work |
| PURGING -> PURGING / bounded worker steps | Persist checkpoint and next retry time with epoch after each acknowledged step; business deletes in short transactions | Database/object/Clerk outage keeps inaccessible state; retry same IDs, not a new deletion |
| PURGING -> DELETED / privacy worker | All live rows/private objects and required identity/provider obligations resolved; suppression receipt mirrored; set root DELETED then hard-remove it; detach minimal receipt owner FK in same final transaction | Store livePurgedAt, residual backup expiry and completedAt separately; report backup residual truthfully |
| DELETED / terminal | No restore/undo transition; explicit new signup has new identity and empty account | Restore procedure below reapplies suppression before any access |

Proposed user deletion assurance: valid Clerk session plus reauthentication within 5 minutes and explicit confirmation of target; freshness comes from a verified server/provider check, never client JSON. The verified Clerk factor-age/reverification adapter is specified in security §16; pinned-SDK behavior remains an acceptance gate. Failure to prove freshness yields 403 REAUTHENTICATION_REQUIRED without mutation. Missing/invalid bearer -> 401; foreign idea/operation -> privacy-preserving 404. Authenticated disabled/deleting account -> 403 for normal routes. Only minimal deletion-status reads and replay of an already accepted same-scope deletion intent may bypass local ACTIVE gating (no new work): verified matching session subject/HMAC, no business reads, no signed downloads; after Clerk identity deletion the session may be unusable and no authenticated status availability is promised. Receipt ID alone grants no access. Fresh account authentication, immediate blocking and recoverable cleanup are approved under P2D-P02; the five-minute window and narrow status projection remain documented engineering defaults requiring SDK validation.

DELETE idea is lifecycle-idempotent: first response is 202 with DataOperation; repeated authorized request resolves the existing operation. Account/idea deletion through POST /me/data-operations uses required Idempotency-Key. A partial unique operation scope permits at most one retained deletion per account identity or idea UUID; this domain dedupe survives ledger expiry. Account deletion subsumes pending idea deletions without erasing their cleanup checkpoints; claim locks ordered account -> idea -> operation prevent conflicting purge ownership. No cancellation/undo endpoint after DELETION_REQUESTED.

Immediate gate means every admission, context assembly, SSE reauthorization, download grant and final write requires account/idea ACTIVE (archive reads use the documented read-only policy). All sensitive writes lock/check lifecycle in the same short transaction; completion before deletion may exist briefly and is purged, deletion first forbids completion. Increment/fence active job epochs; PENDING/RUNNING generations request cancellation, then settle CANCELLED by coordinator if lease fenced; completed history remains terminal until purge. Research/export jobs QUEUED/RUNNING -> CANCELLED; queue removal/abort is best effort, never the safety boundary. Redis outage leaves a durable outbox and DB scanner that continues deletion work. No network call inside a DB transaction.

### Purge checkpoints and storage races

DataOperation.cleanupCheckpoint is versioned JSON, bounded to 32 KiB: schemaVersion=1, phase (FENCE, INVENTORY, STORAGE, CONTENT, IDENTITY, VERIFY, RECEIPT), lastBatchCursor (opaque <=512 chars), counts (nonnegative integers), manifestObjectKey (private opaque <=600 chars), manifestSha256, storagePasses, providerObligations (allowlisted provider/category/state/reference codes only, max 10), backupResidualUntil and lastVerifiedAt. No content, email, token or public URL. A private encrypted JSONL manifest in existing storage records exact object keys/version IDs and deletion acknowledgments, in bounded streamed batches; it survives source-row removal. Keep its object key in the operation until clean, then erase the detailed manifest and retain only receipt hash/counts.

Fence and stop new admissions first. All upload-capable jobs acquire the account/idea lifecycle gate and register their attempt-specific object prefix before upload; future upload attempts require a current epoch. Purge waits for previous upload leases to expire and bounded in-flight upload deadlines, aborts multipart sessions, then performs a second complete prefix/version listing. A worker with a late successful upload cannot commit it; it must schedule orphan cleanup. The second pass covers uploads after the first listing. No completion while known uploads or provider deletions remain uncertain. Delete all storage versions, not only delete markers; unknown buckets, retention locks or unreachable inventory produce REQUIRES_ATTENTION, never false success. Expired grant signatures cannot be recalled universally: recommend 5-minute grants, deny API proxy downloads immediately, remove source objects as early as possible and disclose deployment-specific residual direct-link validity; immediate API denial does not claim universal signed-URL revocation.

Delete in FK-safe batches: evidence links/learnings, memory revisions/proposals then memories, assistant response messages before attempts (break response references without editing message content only inside purge transaction if FK cycles require), user messages after attempts, research/evidence in relation order, exports then snapshots, conversations, idea; usage/outbox/ledger/audit private refs are erased or detached. Actual cyclic FK delete order must be proved by the PostgreSQL test; purge primitive may delete the response Message first, then GenerationAttempt, then trigger Message because AttemptResponse FK is from response to attempt. Root account last; unrelated ideas are never in an idea purge scope. The receipt and identity tombstone have no content-bearing parent cascade. Lease/retry state never depends on a row already deleted.

### Immutability exception and least privilege

Normal API, job, migration and export roles do not bypass revision/snapshot immutability. Design a dedicated NOLOGIN fl_purge_owner role owning only the reviewed SECURITY DEFINER purge entry point [a database procedure running with its owner's restricted permissions]. Ordinary API/worker login roles cannot SET ROLE to it, alter/disable triggers or write guard functions; database-owner credentials never run the application. A separate privacy worker login has EXECUTE only on that entry point, no direct content SELECT/DELETE. The entry point validates operation ID, matching live leaseEpoch, PURGING state, target account/idea scope and allowlisted batch phase; locks operation/lifecycle rows; fixes search_path and resolves qualified object names; deletes only authorized rows; writes counts/checkpoint atomically. No arbitrary SQL, table name, idea list, session-variable-only bypass or global trigger switch is accepted.

Guard contract: normal UPDATE of approved snapshot/revision always fails. DELETE may pass only while current_user=fl_purge_owner and the operation passed in transaction-local context is PURGING with matching epoch and row idea scope. An API can set a custom PostgreSQL variable, so variables alone are insufficient authorization. The helper is security INVOKER, not DEFINER; callers cannot elevate through it. Function/role DDL is an implementation-stage migration acceptance gate; detailed predicate is in physical-design §13 and guards.sql. Delete audit is minimal operation/step/count, not a duplicate private-content history.

### Restore, partial failures and completion semantics

Retry profile: 5 automatic attempts per step, exponential jitter 5 seconds to 5 minutes, then REQUIRES_ATTENTION with alert; an operator may re-drive the same operation/epoch claim after fixing the cause. DB scanner checks eligible operations every proposed 30 seconds independent of Redis. Provider retries honor provider limits. A deadline marks stalled work for attention; it never reopens private access or drops an incomplete operation at TTL.

Backups remain inaccessible for ordinary reads and expire under approved limits. Before exposing a restored database, restore in isolation, load the latest externally mirrored deletion/suppression manifest, compare its watermark and receipt IDs against pre-restore deletion records/WAL and provider deletion reconciliation, reapply gates and purge all listed scopes/objects, restore current tombstones/receipts, then verify no suppressed identities/scopes are visible. An old restored DB alone cannot prove it knows later deletions. If the latest complete manifest or accepted-but-not-mirrored requests cannot be established after disaster, keep service closed and reconcile from surviving WAL/primary metadata/provider records; do not claim a guaranteed deletion-safe restore across an unmeasured loss window. Completion requires suppression mirroring acknowledgment, but even accepted incomplete requests must be reconciled before reopening.

Account export reuses DataOperation(kind=EXPORT), not a new entity. Capture owned rows/versions in a bounded repeatable-read transaction into memory (maximum proposed 20 MiB); commit before any upload. Enumerate requested data, schemas and provenance without provider secrets, cross-owner data or internal-only security records. Upload the captured private JSONL manifest outside the transaction, then pin its cutoff/key/hash under operation lease and active lifecycle in a new transaction. Crash before pinning permits a fresh capture/cutoff and orphan cleanup; after pinning all retries use that manifest. Report the final captured cutoff, not the request time. A streaming export worker reads the pinned manifest, not changing live rows, then uploads a checksummed archive. No unbounded transaction across render/upload. Privacy deletion invalidates grants/manifests/artifacts even during export. Export content manifest references only authorized IDs and is part of erasure. Proposed format: ZIP of versioned JSON plus README, checksums and approved PDFs already available; Pending Product Approval. No automatic export before deletion.

## Current physical names and context removal

Snapshot document version is version, mutable preview CAS is draftRevision, hash is contentSha256. ConfirmedMemory.version DTO maps currentVersion. Memory deletion/context synchronization is specified in API contracts §13; proactiveResearch in §15. Research/export deletion cancellation QUEUED/RUNNING -> CANCELLED is coordinator-authorized under epoch fencing; CANCELLED is terminal. These lifecycle states never become confirmed facts or new generation states.


During account PURGING, coordinator marks each owned child idea PURGING under the same account gate before scoped batch deletion; it preserves/subsumes any previously requested idea operation. The root/operation transition contract is consistent even if account already has no ideas. No database row deletion substitutes for storage/identity acknowledgment.


### Approved active-system target and remaining retention settings

P2D-P01 supersedes only the former 7-day live-purge proposal, not the separate 7-day backup recommendation or PDF cache proposal. Active-system scope covers live database private content, application-managed storage versions/manifests and application caches. BackupResidualUntil records actual backup-copy expiry separately; provider-held copies/contractual obligations are tracked separately and disclosed. A missed active-system target remains visible in REQUIRES_ATTENTION and never permits renewed access or a false completion receipt. DataOperation.policyVersion=p2d-privacy-v2 binds the approved direction; its activePurgeTargetAt is derived as requestedAt + 30 days for deletion operations (not the execution lease deadline). Export operations have no purge target. Version v1 remains historical and must not be silently reinterpreted on an existing receipt. No runtime activation or provider compliance is implied by documentation approval.
